Both Mapillary and KartaView publish the bulk of their user-contributed imagery under the Creative Commons Attribution-ShareAlike 4.0 International (CC BY-SA 4.0) license.14 While this is an open license, its application to our specific commercial use case requires careful legal scrutiny. The research will engage legal counsel to provide a definitive opinion on the following activities: Programmatic, large-scale downloading of images via the API for analysis. Storing these images temporarily in a caching system for processing. Creating derivative works, specifically the "before-and-after" visualizations where our AI overlays new products onto the original images.1 Displaying these derivative works to our B2B clients as part of a paid service. Fulfilling the attribution requirements of the CC BY-SA license within our platform's user interface in a way that is both compliant and user-friendly. It is important to note that some specialized datasets from Mapillary, such as the Vistas and Metropolis datasets, are provided under a more restrictive non-commercial license (CC BY-NC-SA), which would make them unsuitable for this project.20 The research must confirm that the general imagery accessible via the public APIs is governed by the commercial-use-friendly CC BY-SA license.

2.2. Multi-Source Image Processing and Caching

To handle the variety of incoming data, a robust ingestion pipeline is required. This pipeline will be responsible for intelligently selecting the best data source, normalizing the imagery for consistent processing, and caching data to optimize performance and cost. Intelligent Source Router: The ImageSourceRouter component, specified as a Python class in the initial plan, will be the first step in the pipeline.1 The research will focus on developing and testing the logic for this router. A key function will be to perform low-cost, preliminary coverage checks before requesting full image data. For instance, it will query Mapillary's coverage vector tiles for a given location to confirm the presence of recent imagery before committing to a more expensive image download API call.12 If Mapillary returns no results, the router will automatically failover to query KartaView, and if both fail, it will fall back to using only the available aerial imagery. This strategy minimizes unnecessary API calls and provides resilience against sparse coverage from any single provider. Image Normalization Pipeline: A standardized image processing pipeline will be developed using the OpenCV library to ensure that all images, regardless of their source, are in a consistent format before being passed to the AI models.33 Research and development tasks for this pipeline include: Source-Specific Corrections: Implementing tailored preprocessing steps for each data source, as outlined in the initial plan.1 This may involve applying gamma correction to KartaView images, which can often have different exposure levels, or using denoising algorithms like cv2.fastNlMeansDenoisingColored on Mapillary images to improve clarity. Illumination and Contrast Handling: Outdoor imagery is subject to highly variable lighting conditions. The research will investigate the use of adaptive thresholding techniques (cv.ADAPTIVE_THRESH_GAUSSIAN_C) and histogram equalization to normalize contrast and make features more prominent, which is crucial for the accuracy of subsequent computer vision algorithms.36 Standardization: All images will be resized to a standard resolution (e.g., 1024x1024 pixels), converted to a consistent color space (e.g., BGR to RGB), and saved in a uniform format to ensure predictable input for the AI analysis stage. Multi-Tier Caching System: To manage costs and improve latency for repeated requests of the same property, a multi-level caching system will be architected as specified in the plan.1 The research will involve performance benchmarking of different technologies to create an optimal hierarchy: In-Memory Cache (L1): A fast, in-memory cache (e.g., using Redis or an LRU cache) for frequently accessed properties. Disk Cache (L2): A local SSD-based disk cache on the processing servers for recently accessed images that have been evicted from the L1 cache. Cloud Cache (L3): A persistent cloud object store (e.g., AWS S3) as the final layer of the cache, storing all processed images for a defined period. Furthermore, a "coverage pre-warming" strategy will be designed. For high-priority geographic areas (e.g., new target markets), a batch process will run during off-peak hours to query imagery and populate the cache, ensuring that initial user requests in these areas are served with minimal latency.1

2.3. AI Computer Vision and Analysis Pipeline

This sub-section details the research plan for the core AI capabilities of the automated engine, which will be built upon a combination of open-source computer vision libraries and the OpenAI Vision API. OCR for Feature Extraction: Accurately identifying a property's address from an image is fundamental to linking visual data with property records. Technology Validation: A proof-of-concept will be developed using Tesseract OCR to extract text from a sample set of street-level images, with a specific focus on the challenging task of recognizing varied fonts and styles of house numbers and street signs.37 Fine-Tuning Research: Standard Tesseract models may perform poorly on non-standard text. Therefore, a critical research task is to implement a fine-tuning pipeline. This involves creating a custom "ground truth" dataset by manually cropping and transcribing hundreds of examples of house numbers and street signs from our target operational areas. The tesstrain toolkit will then be used to retrain the Tesseract neural network model, creating a specialized language model optimized for our specific use case.39 The success of this fine-tuned model is a key dependency for the entire automated system. Computer Vision for Condition Assessment (OpenCV): The platform will use a suite of OpenCV-based algorithms to detect specific physical conditions of a property. The research will focus on developing and validating models for the use cases outlined in the PropertyInsight AI documentation.1 This includes: Paint Degradation: Implementing algorithms that analyze the HSV (Hue, Saturation, Value) color space of a building's exterior. Areas with low saturation and high variance in pixel values are strong indicators of faded or peeling paint.1 Structural Damage: Utilizing a combination of Canny edge detection to highlight outlines, contour detection to identify shapes, and Hough transforms to find lines and circles. These techniques can be combined to detect anomalies such as cracks in walls, dents in garage doors, or missing roof shingles.34 Specialized Damage Detection: The research will extend to more specific and high-value use cases. For hail damage, the system will be trained to detect patterns of small, circular indentations on surfaces like car hoods or siding.2 For water damage, the focus will be on detecting discoloration, staining patterns, and material deformation on interior and exterior walls. This may also involve investigating the potential of analyzing thermal imagery if such data were available.4 Semantic Interpretation (OpenAI Vision API): While OpenCV is excellent for detecting quantifiable features, a higher level of semantic understanding is required for a complete property assessment. The OpenAI Vision API (e.g., GPT-4o) will be used for this purpose.40 Prompt Engineering: The core research task is to develop a library of sophisticated and reliable prompts that instruct the model to analyze an image and provide a nuanced assessment. Prompts will be carefully engineered to go beyond simple object detection, asking the model to: Assess the overall "curb appeal" and provide a qualitative rating. Identify the architectural style of the property (e.g., "Colonial," "Modern," "Craftsman"). Detect complex, subjective conditions that are difficult for traditional CV models, such as "overgrown landscaping," "visible signs of neglect," or "outdated exterior fixtures." Crucially, prompts will instruct the model to return its analysis in a structured JSON format, specifying the required fields and data types. This ensures the output is consistent and can be easily parsed and integrated into the platform's database without requiring complex NLP on the response.40 Cost and Latency Analysis: As the OpenAI API is a metered service, a thorough performance and cost analysis will be conducted. This will involve benchmarking the cost-per-analysis and average response time for our specific prompts to ensure that its use is financially viable and performant enough for a large-scale processing workflow. The development of this automated pipeline reveals a fundamental challenge: its reliance on a chain of technologies, each with its own potential for failure, makes the entire system inherently "brittle." The availability and quality of open-source imagery can be inconsistent, OCR may fail on non-standard text, and computer vision models can be confused by ambiguous visual data like shadows or reflections. A purely automated system would therefore be forced to either discard a significant percentage of properties for which it has low confidence or operate with an unacceptably high error rate. This is where the true strategic value of the unified architecture becomes apparent. The Live Inspection Service is not merely a separate tool but the intelligent fallback and data enrichment mechanism for the automated pipeline. The system must be designed so that a low-confidence result from the automated analysis—for example, a potential roof issue flagged with only 60% certainty—automatically generates a high-priority "verification task." This task dispatches a gig worker to the property to capture targeted, high-resolution video of the roof, providing the definitive "ground truth" needed for a confident assessment. This integration transforms the live service from a reactive, client-driven tool into a proactive, essential component of the core analysis engine, ensuring the reliability and value of the platform's output.

III. Research & Development Plan for the Live Inspection Service

This section outlines the research and development plan for the "See What I See" live inspection service. The focus is on creating a robust, low-latency, and feature-rich platform that empowers remote experts to effectively guide on-site gig workers. The research will address key technical challenges in real-time communication, cross-platform mobile development, and interactive user interface design.

3.1. WebRTC Backend and Communication Protocol

The backbone of the live inspection service is a real-time communication infrastructure built on WebRTC. This requires a reliable signaling mechanism and a well-defined protocol for data exchange. Signaling Server Architecture: A signaling server is required to orchestrate the connection between the gig worker's mobile client and the expert's web client. The research will involve prototyping and load-testing a signaling server based on the architecture outlined in the planning documents, using Node.js and the Socket.IO library.1 The architecture must be designed for high availability and scalability, capable of managing user presence, session initiation protocol (SIP) handshakes, and peer discovery for potentially thousands of concurrent inspection sessions. Data Channel Protocol Definition: The WebRTC data channel provides a powerful, low-latency conduit for sending arbitrary data directly between peers, separate from the audio/video streams.45 A critical design task is to define a structured, extensible communication protocol, likely using JSON, to be transmitted over this channel. This protocol will be the language of interaction between the expert and the gig worker. The research will define message types and schemas for: Annotation Commands: Messages for rendering graphics on the gig worker's screen. This will include commands like drawCircle({x, y, radius, color}), drawArrow({startX, startY, endX, endY, color}), and addText({x, y, text, color}). Coordinates will be normalized (e.g., 0.0 to 1.0) to be independent of screen resolution. Remote Control Commands: A command set allowing the expert to control the gig worker's device to ensure optimal data capture. This will include commands such as takePhoto(), startRecording(), stopRecording(), toggleFlash(), switchCamera() (front/rear), and setZoom({level}). Telemetry Data: Messages sent from the mobile client to the expert dashboard to provide enhanced situational awareness. This will include periodic updates of the device's GPS coordinates, compass heading, and gyroscope/accelerometer data to show the phone's orientation in 3D space. TURN/STUN Server Strategy: WebRTC connections can often fail when peers are behind restrictive firewalls or Network Address Translators (NATs). STUN (Session Traversal Utilities for NAT) servers are used to discover public IP addresses, and TURN (Traversal Using Relays around NAT) servers are used to relay traffic when a direct peer-to-peer connection is impossible. The research will involve: Testing the reliability of public STUN servers for initial development. Evaluating managed TURN server providers (e.g., Twilio) versus the operational cost and complexity of deploying and maintaining a self-hosted open-source solution like Coturn. A robust TURN server strategy is non-negotiable for ensuring a reliable service for enterprise clients.

3.2. Gig Worker Mobile Client (iOS & Android)

The gig worker's mobile application is the primary tool for on-site data capture. The choice of technology stack for this client is a critical architectural decision with long-term implications for performance, feature development, and maintenance costs. Cross-Platform Technology Evaluation: A formal trade-off analysis will be conducted to select the optimal mobile development framework. The evaluation will compare three primary approaches: Native Development (Swift for iOS, Kotlin for Android): Offers the best possible performance and deepest integration with device hardware, which is critical for demanding tasks like real-time video encoding and camera control. However, it requires maintaining two separate codebases. React Native: Allows for a large portion of the codebase to be shared between iOS and Android. The research will focus on the maturity and performance of key libraries, such as react-native-webrtc for communication and AR libraries like ViroReact for the annotation overlay.47 Flutter: Another popular cross-platform framework. The research will evaluate its real-time video performance and the capabilities of its AR libraries, such as ar_flutter_plugin.50

The final decision will be based on a weighted scoring of criteria including performance, access to native APIs, library maturity, and developer ecosystem. AR Annotation Overlay Implementation: The ability for an expert to draw on the live video feed is a core feature. Initial 2D Overlay Approach: As recommended in the planning documents for reasons of simplicity, performance, and cost, the initial implementation will focus on a 2D overlay.1 This involves rendering the live video stream to a view and placing a transparent canvas (e.g., an HTML5 Canvas in a WebView or a native drawing view) on top of it. Incoming annotation commands from the data channel are then used to draw shapes and text onto this canvas. Advanced 3D "World-Locked" Annotations: A parallel research track will explore the feasibility of using native AR frameworks (ARKit for iOS, ARCore for Android) to create more immersive, "world-locked" annotations.52 This would use Simultaneous Localization and Mapping (SLAM) to allow an expert to, for example, draw a circle around a specific crack in a wall, and have that virtual circle remain anchored to the physical crack as the gig worker moves their phone. This advanced feature would provide significant value in many inspection use cases. Libraries that abstract these native frameworks, such as ViroReact or ar_flutter_plugin, will be prototyped and evaluated for performance and ease of integration.48 High-Resolution Media Capture Challenge: A key technical risk identified in the documentation is the "single camera resource" limitation on most mobile operating systems, which typically prevents an application from simultaneously running a live video stream and accessing the camera to take a separate, high-resolution photo.1 The research must devise a robust solution: Native API Investigation: The first step is to conduct a deep investigation of the latest iOS and Android camera APIs to confirm if any new capabilities allow for concurrent access or a non-disruptive high-resolution capture during a video session. "Pause-Capture-Resume" Workflow Prototyping: Assuming concurrent access is not possible, the primary research path will be to prototype the "pause-capture-resume" workflow. This involves: (a) sending a signal to the expert UI that a capture is in progress, (b) momentarily stopping the WebRTC video track, (c) immediately accessing the native camera API to capture a full-resolution photo, (d) releasing the camera resource, and (e) restarting the WebRTC video track. The key metric for this research will be the total "blackout" duration experienced by the remote expert. The goal is to minimize this interruption to under 2-3 seconds to maintain a fluid user experience. Stream Frame-Grabbing as a Fallback: As a simpler but lower-quality alternative, the research will evaluate the feasibility of grabbing a single frame directly from the WebRTC video stream. This requires testing the maximum stable video resolution (e.g., 1080p, 4K) that can be maintained over typical 4G/5G cellular networks and determining if the resulting image quality is sufficient for use cases that do not require maximum fidelity.

3.3. Expert Web Client and Control Interface

The expert web application is the command center for the live inspection service. Its design must prioritize efficiency, clarity, and control, enabling an expert to seamlessly manage a remote inspection. UI/UX Design for a Real-Time Dashboard: The design of the expert dashboard is a complex human-computer interaction challenge. It must present a high density of information without overwhelming the user. Research into best practices for real-time operational dashboards will be conducted to inform the design.56 The final UI must allow an expert to fluidly perform multiple actions in parallel: Monitor the main low-latency video feed. View a side panel containing contextual data about the task, such as property information pushed from the Automated Analysis Engine. Access an intuitive toolkit for drawing annotations on the video feed. Use a dedicated control panel to trigger remote camera actions on the gig worker's device. Browse a gallery of photos and video clips captured during the current session. State Management for Real-Time Applications: The expert dashboard is a highly dynamic, state-intensive application. The UI must react instantly to a constant stream of incoming data from the WebRTC data channel (e.g., new telemetry, status updates) and user interactions. To manage this complexity and prevent performance bottlenecks, the research will evaluate and select a modern frontend state management library. Redux is a strong candidate due to its predictable state container and robust ecosystem, but lighter-weight alternatives like Zustand or MobX will also be considered for their simpler APIs.57 The chosen solution must be capable of handling high-frequency state updates without causing UI lag or unnecessary re-renders. Web-Based Video and Annotation Rendering: A prototype of the client-side functionality will be built. This will involve using the browser's native WebRTC APIs (or a wrapper library like simple-peer) to establish the connection and render the incoming video stream into a standard HTML element. The research will focus on the most efficient way to implement the annotation layer. The primary approach will be to overlay a transparent HTML5 element directly on top of the video element. As annotation commands arrive via the data channel, JavaScript will be used to draw the corresponding shapes, lines, and text onto the canvas in real-time.

IV. System Integration, Deployment, and Scalability Architecture

This section outlines the plan for unifying the automated analysis engine and the live inspection service into a single, cohesive platform. It also details the strategy for deploying this platform on a modern, scalable, and resilient cloud infrastructure capable of supporting growth from an initial MVP to a large-scale enterprise service.

4.1. Unified API Gateway and Microservices Architecture

A modern microservices architecture will be adopted to ensure the system is modular, maintainable, and independently scalable. Unified API Gateway: A single, unified API Gateway will be designed to serve as the sole entry point for all client applications (the gig worker mobile app and the expert web app). This gateway will be responsible for request routing, authentication, rate limiting, and protocol translation, providing a consistent and secure interface to the backend services. Microservices Architecture: The backend logic will be decomposed into a set of discrete, independently deployable microservices, as proposed in the initial planning documents.1 The research will focus on defining the precise boundaries, responsibilities, and API contracts for each service. Key services will include: UserManagement Service: Handles user registration, authentication, profiles, and roles (gig worker, expert, client). TaskDispatch Service: Manages the lifecycle of inspection tasks, from creation and assignment to completion and payment. AutomatedAnalysis Service: Contains the logic for the property analysis pipeline, including interaction with external geospatial APIs and the AI models. WebRTCSignaling Service: The dedicated signaling server responsible for orchestrating WebRTC connections. MediaStorage Service: Provides an abstraction layer for uploading, storing, and retrieving photos and videos.

4.2. Containerization and Orchestration (Docker & Kubernetes)

To facilitate agile development, consistent environments, and automated scaling, the platform will be built on a foundation of containers and orchestration. Containerization with Docker: A containerization strategy will be developed where each microservice is packaged into a lightweight, portable Docker container. This ensures that each service runs in an identical environment from local development through to production, eliminating "works on my machine" issues. Orchestration with Kubernetes: Kubernetes will be used to automate the deployment, scaling, and management of the containerized services.60 The research and planning in this area will focus on: Defining Kubernetes Resources: Creating the necessary Kubernetes configuration files (YAML manifests) for deployments, services, pods, and ingress controllers to define the desired state of the application. Implementing Auto-Scaling: Configuring Horizontal Pod Autoscalers (HPAs) to automatically adjust the number of running container instances based on real-time demand. For example, the AutomatedAnalysis Service can be scaled up during off-peak hours for large batch processing jobs, while the WebRTCSignaling Service can be scaled up during peak business hours to handle a high volume of live inspections. Establishing a Monitoring Stack: Implementing a comprehensive logging, monitoring, and alerting stack using industry-standard tools like Prometheus for metrics collection, Grafana for visualization and dashboards, and the ELK Stack (Elasticsearch, Logstash, Kibana) for centralized logging. This is essential for maintaining system health and troubleshooting issues in a distributed environment.

4.3. Data Persistence and Storage Strategy

A multi-faceted data storage strategy is required to handle the different types of data the platform will generate and consume. Project Database: A relational database, such as PostgreSQL, will be evaluated and selected as the primary data store. It will house structured data including user profiles, task details, property information, and the structured JSON output from the AI analysis engine. Its transactional integrity and powerful querying capabilities make it ideal for this core operational data. Media Storage: The high-resolution photos and videos captured by the live inspection service represent a significant storage challenge. The architecture will utilize a cloud-based object storage service, such as AWS S3, for this purpose.1 This provides virtually unlimited scalability, high durability, and cost-effective storage. To ensure fast retrieval of media within the expert web client, a Content Delivery Network (CDN) like Amazon CloudFront will be integrated to cache media at edge locations closer to the users. AI Training Data Lake: To enable the "data flywheel," a dedicated storage solution is needed for the data used to retrain the LuminatingCore AI models. A data lake architecture will be planned, likely using AWS S3 as the underlying storage. A pipeline will be designed to collect the verified data from the live inspection service (images, videos, annotations), anonymize it to remove any personally identifiable information (PII), and structure it in a format that is optimized for consumption by machine learning training frameworks like TensorFlow or PyTorch.

V. Navigating the Data, Legal, and Ethical Landscape

The successful deployment of this platform depends not only on technical excellence but also on a rigorous and proactive approach to managing the significant legal, privacy, and ethical risks inherent in its operation. The research outlined in this section is as critical as the technical R&D and must be conducted in parallel to ensure a responsible and sustainable business model.

5.1. Data Privacy and Regulatory Compliance

The platform will handle a variety of data, some of which may be considered sensitive or personal under various legal frameworks. Strict adherence to privacy laws is paramount.1 Comprehensive Legal Audit: The project will engage legal and compliance experts with expertise in data privacy to conduct a full audit of the proposed system architecture and data flows. This audit will assess compliance with key regulations, including the General Data Protection Regulation (GDPR), the California Consumer Privacy Act (CCPA), the Fair Credit Reporting Act (FCRA), and the Gramm-Leach-Bliley Act (GLBA), particularly for use cases in the financial and insurance sectors.1 Data Protection Impact Assessment (DPIA): The output of this legal research will be a formal DPIA. This document will systematically identify potential privacy risks at each stage of the data lifecycle—from collection and processing to storage and deletion. For each identified risk, the DPIA will prescribe specific mitigation strategies. These strategies will include technical measures like end-to-end encryption and robust anonymization techniques, as well as procedural measures such as implementing clear data minimization policies and designing transparent user consent workflows for data collection.

5.2. API Terms of Service and Licensing Adherence

The platform's reliance on a multitude of third-party APIs necessitates a disciplined approach to compliance with their terms of service and licensing agreements. Compliance Matrix: Building on the initial research in Section 2.1, a detailed compliance matrix will be created and maintained. This living document will map every external API used by the platform (Mapillary, KartaView, Mapbox, OpenAI, etc.) to its specific terms of service. For each API, the matrix will document our exact use case, the relevant licensing clauses, and any obligations or restrictions (e.g., attribution requirements, rate limits, prohibitions on data caching or resale). Developer Policy and Governance: The compliance matrix will form the basis of a clear "Rules of Engagement" policy for the engineering team. This policy will provide developers with unambiguous guidance on the acceptable use of each API, ensuring that the platform remains in full compliance as it evolves. Regular reviews of this policy will be scheduled to account for any changes in third-party terms.

5.3. Ethical Framework for "Micro-Investigations"

The expansion of the gig-work platform into services that support skiptracing, private investigation, and door-knocking carries significant ethical responsibilities and potential for misuse.1 A robust ethical framework is not an optional add-on but a core requirement for the platform's social license to operate. Defining Strict Operational Boundaries: The research will involve collaboration with legal and ethics professionals to establish a clear and unambiguous set of guidelines defining acceptable and unacceptable tasks. This "Code of Conduct" will be programmatically enforced where possible and will explicitly prohibit any activities that could be construed as illegal surveillance, harassment, stalking, or trespassing.1 All tasks must be conducted in public spaces or with the explicit consent of the property owner. Mandatory User Training and Vetting: A comprehensive, mandatory training and certification program will be developed for all gig workers who wish to perform "micro-investigation" tasks. The research will focus on designing a curriculum that covers: Legal Boundaries: Clear instruction on privacy laws, trespassing laws, and the limits of acceptable observation. Privacy Rights: Education on respecting the privacy of individuals. De-escalation Techniques: Training on how to interact with the public professionally and safely, and how to de-escalate any potential confrontations. Platform Code of Conduct: A rigorous test to ensure understanding of and agreement to the platform's ethical guidelines. Implementing Technology Safeguards: The platform will be engineered with features designed to enforce ethical use and minimize risk. Research will investigate the implementation of: Geofencing: Using GPS data to create virtual boundaries around a target property to alert users if they are about to trespass onto private land. Automated PII Redaction: Investigating the use of computer vision libraries to automatically detect and blur faces and license plates in any media captured through the platform, reducing the risk of inadvertent privacy violations.61 Immutable Audit Trails: Creating a secure, auditable log of all task assignments, user actions, and data collected. This ensures transparency and accountability for all activities conducted on the platform.

VI. Phased Implementation and Validation Roadmap

This section presents a pragmatic, multi-phase roadmap for executing the research and development plan. The roadmap is designed to manage risk by addressing the most critical unknowns first, deliver value incrementally, and allow for iterative learning and adaptation throughout the project lifecycle.

6.1. Phase 1: Foundational Research & Core Service Prototyping (Months 1-3)

The primary objective of Phase 1 is to de-risk the project by tackling the most significant technical and legal uncertainties. This phase is focused on validation and prototyping rather than building production-ready features. Objectives: Achieve legal certainty regarding the use of open-source imagery for our commercial platform. Validate the technical feasibility of the multi-source data ingestion pipeline. Prove the core real-time communication functionality of the live inspection service. Find a definitive solution to the high-resolution media capture challenge on mobile devices. Deliverables: Legal Viability Report: A conclusive legal opinion on the commercial use of imagery under the CC BY-SA 4.0 license, based on the research in Section 2.1. Data Ingestion Prototype: A working prototype of the ImageSourceRouter and the OpenCV-based image normalization pipeline. WebRTC Proof-of-Concept: A functional prototype demonstrating a stable, 1-to-1 WebRTC video stream between a mobile client and a web client, with a basic data channel for sending simple messages. Media Capture Validation Report: A technical report detailing the findings on the "single camera resource" problem, including measured "blackout" times for the "pause-capture-resume" workflow and an assessment of its impact on user experience.

6.2. Phase 2: Minimum Viable Product (MVP) Development (Months 4-9)

With foundational risks addressed, Phase 2 focuses on building and launching an end-to-end, integrated MVP. The scope will be tightly focused on a single, high-value market vertical, such as insurance property claims, to prove the core value proposition. Objectives: Build and deploy a functional, end-to-end version of the unified system. Validate the core "data flywheel" concept with an initial integration point. Acquire the first set of pilot customers in the target vertical to gather real-world feedback. Deliverables: MVP of Automated Analysis Engine: A deployed service capable of analyzing properties using one street-level source (Mapillary) and one aerial source (Mapbox). It will feature initial computer vision models trained to detect a single class of damage (e.g., roof damage). MVP of Live Inspection Service: A cross-platform mobile app (based on the technology decision from Phase 1) and a web-based expert dashboard. The MVP will support 2D annotations and remote photo capture. 'use client';

import { useEffect, useRef, useState } from 'react';
import mapboxgl from 'mapbox-gl';
import 'mapbox-gl/dist/mapbox-gl.css';

mapboxgl.accessToken = process.env.NEXT_PUBLIC_MAPBOX_TOKEN || '';

interface MapViewProps {
  storms: any[];
  selectedStorm: string | null;
  onPropertySelect: (properties: string[]) => void;
}

export function MapView({ storms, selectedStorm, onPropertySelect }: MapViewProps) {
  const mapContainer = useRef<HTMLDivElement>(null);
  const map = useRef<mapboxgl.Map | null>(null);
  const [lng] = useState(-97.5);
  const [lat] = useState(32.7);
  const [zoom] = useState(9);

  useEffect(() => {
    if (!mapContainer.current) return;

    map.current = new mapboxgl.Map({
      container: mapContainer.current,
      style: 'mapbox://styles/mapbox/dark-v11',
      center: [lng, lat],
      zoom: zoom,
    });

    map.current.addControl(new mapboxgl.NavigationControl(), 'top-right');

    // Add storm markers
    storms.forEach((storm) => {
      const el = document.createElement('div');
      el.className = 'storm-marker';
      el.style.backgroundColor = getStormColor(storm.severity);
      el.style.width = '30px';
      el.style.height = '30px';
      el.style.borderRadius = '50%';
      el.style.border = '3px solid white';
      el.style.cursor = 'pointer';

      new mapboxgl.Marker(el)
        .setLngLat([storm.location.lng, storm.location.lat])
        .setPopup(
          new mapboxgl.Popup().setHTML(`
            <div style="color: black; padding: 8px;">
              <strong>Storm Event</strong><br/>
              Hail: ${storm.hailSize}" <br/>
              Wind: ${storm.windSpeed} mph<br/>
              Severity: ${storm.severity}/10
            </div>
          `)
        )
        .addTo(map.current!);
    });

    return () => {
      map.current?.remove();
    };
  }, [storms]);

  function getStormColor(severity: number): string {
    if (severity >= 8) return '#ef4444'; // red
    if (severity >= 5) return '#f97316'; // orange
    return '#eab308'; // yellow
  }

  return (
    <div className="relative w-full h-full">
      <div ref={mapContainer} className="w-full h-full rounded-lg" />
      
      {/* Map Legend */}
      <div className="absolute bottom-4 right-4 bg-slate-900/90 backdrop-blur-sm p-4 rounded-lg border border-slate-700">
        <div className="text-white font-semibold mb-2">Storm Severity</div>
        <div className="space-y-2 text-sm">
          <div className="flex items-center gap-2">
            <div className="w-4 h-4 rounded-full bg-red-500" />
            <span className="text-gray-300">High (8-10)</span>
          </div>
          <div className="flex items-center gap-2">
            <div className="w-4 h-4 rounded-full bg-orange-500" />
            <span className="text-gray-300">Medium (5-7)</span>
          </div>
          <div className="flex items-center gap-2">
            <div className="w-4 h-4 rounded-full bg-yellow-500" />
            <span className="text-gray-300">Low (1-4)</span>
          </div>
        </div>
      </div>
    </div>
  );
}
